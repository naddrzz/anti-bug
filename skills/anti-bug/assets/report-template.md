# Anti-Bug Report - [Project]

Structure for `docs/anti-bug-report.md`. Sections 4, 5 and 11 are generated by
`python scripts/ledger.py report`; the rest is written around them. The document
has to stand alone for someone who never saw the session, so resolve every
"[...]" and delete anything that does not apply rather than leaving a heading empty.

---

## 1. Metadata

- Date:
- Branch / commit range:
- Scope: what was swept, and what was deliberately excluded
- Environment: OS, runtime versions, how the app was run
- Tooling actually executed (and anything that could not run, with the reason)

## 2. Executive summary

Two or three paragraphs, written for someone deciding whether to ship.

- What was reviewed and how deeply
- Totals: findings by severity; fixed / false positive / needs decision / deferred
- **Release readiness: Ready | Ready with conditions | Not ready** - with the conditions spelled out
- Top 3 risks, each in one sentence naming the impact rather than the code smell

## 3. Project context

Condensed Context Summary from Phase 0: purpose and users, stack and versions,
architecture and main data flow, external integrations, auth model, and the
blast-radius ranking that drove the sweep order. Include the assumptions made
where information was missing - the next reader needs to know which conclusions
rest on them.

## 3b. Business rules register

[ledger.py report output]

The rules the business-logic findings were judged against. Flag every rule marked
`inferred` here explicitly: those were derived from the code rather than stated by
the business, so any finding resting on one is a question for a product owner, not
a settled defect. Listing them is how the next reader knows which conclusions are
provisional.

## 10. Not fixed

[ledger.py report output] - expand each *Needs decision* item with the options,
their trade-offs, and a recommendation. Someone has to act on these; give them
enough to decide without re-reading the code.

## 11. New issues discovered during remediation

Problems found while fixing that were not in the original sweep, with severity
and current status. These are recorded rather than quietly fixed because they
change the risk picture.

## 12. Changes affecting others

Anything that touches API contracts, database schemas, configuration, env vars,
or dependencies - with migration steps and rollback instructions. If nothing
changed here, say so explicitly; "no section" and "no changes" read the same
and mean different things.
